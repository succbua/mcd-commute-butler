# 示例三 · 临界时段（到达即停售）

## 场景

09:55 出门，40 分钟车程 → 10:35 到店。
早餐供应 10:30 结束。**到达时早餐刚好停售。**

这是通勤点单里最典型的"白跑一趟"场景，也是本项目最想解决的问题。

## 复现命令

```bash
node scripts/plan-commute-order.mjs --input examples/payload-boundary.json
```

## 这个结果说明了什么

**1. 3 个早餐专属餐品被正确剔除。**
`咖啡可颂套餐`、`早安咖啡组合`、`原味豆浆` 的可售时段被标记为 `breakfast`，
到达时间 10:35 已属正餐时段，全部被过滤，并在提示中明确告知数量。

如果用户此刻还在路上、想看方案 3 里那个「满 20 减 12」的券能不能用，
他看到的会是一个**真买得到**的正餐方案（麦辣鸡腿堡 ¥9），而不是一个到店后发现买不了的早餐方案。

**2. Skill 层会追加临界告警。**
本 Demo 里到达时距正餐时段结束还有 205 分钟，不构成临界。
按 `reference/time-window-rules.md` 的规则，若窗口剩余不足 30 分钟，
Skill 必须在回复最前面输出：

```
⚠ 你到达时距早餐供应结束仅剩 N 分钟，建议现在就下单预约。
```

并把「取餐耗时」权重从 0.30 临时提到 0.50，优先推荐出餐快的组合。

**3. 真正的解法是"提前预约"，不是"改吃别的"。**
`create-order` 支持预约。09:55 出发时如果立刻下单预约 10:20 取餐，
用户仍能吃上早餐。所以面对临界情况，Skill 的正确动作是：
**先提示可以赶末班车（预约），再给出赶不上的备选方案**，让用户自己选。

## 怎么自己复现临界状态

把 `examples/payload-boundary.json` 里的 `departTime` 改成 `09:30`，
到达时间变成 10:10，此时距早餐结束只剩 20 分钟 —— 触发临界判定。
