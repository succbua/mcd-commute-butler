# 示例一 · 早八通勤抢早餐

## 用户输入

```
我 8:20 出门，40 分钟到公司，预算 40，想喝咖啡
```

## 复现命令

```bash
node scripts/plan-commute-order.mjs --demo
```

## 这个结果说明了什么

**1. 时段过滤真的生效了。**
菜单里的「双层吉士汉堡」属于正餐时段，到达时（09:00）不可售，被自动剔除并在提示中说明。
不是悄悄丢掉，而是明确告知用户「过滤掉了什么」。

**2. 券的时间价值被主动纳入决策。**
方案 3「早安咖啡组合」原价 ¥22，用掉的是 **1.7 天后就过期** 的「满 20 减 12」券，
实付 ¥10 —— 比方案 2 的 ¥12 还便宜。这正是本项目的核心差异：**不只看「哪张券能用」，而是看「哪张券不用就浪费了」。**

**3. 但它依然不是推荐方案。**
方案 1 的评分（81）显著高于方案 3（57.5），因为：
- 价格 ¥9 < ¥10
- 热量 10 kcal << 380 kcal
- 取餐耗时 6 分钟 < 8 分钟

**引擎没有为了"用掉快过期的券"而牺牲用户的其他利益**，而是把这张券的价值量化后放进四维评分里参与竞争。
如果用户的偏好是「今天想吃点扎实的」，只要提高 `weights.calories` 的反向权重或直接指定偏好，
方案 3 就会浮上来。这是"给出取舍"而不是"替用户拍板"。

**4. 三个方案互不相同。**
选取逻辑优先覆盖「最优 / 最省 / 最低热量」三种取向，不足时按评分顺位补齐，
避免出现三个一模一样的方案。
