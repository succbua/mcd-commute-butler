# 异常与降级策略

本文件规定各类异常下应有的行为。核心原则：**宁可明确说"拿不到"，也不要编造。**

## 1. 门店类异常

| 情况 | 表现 | 处理 |
|---|---|---|
| 附近无门店 | `query-nearby-stores` 返回空 | 告知用户并建议：①换目的地地址 ②改用外送 ③放宽距离范围。不要虚构门店 |
| 门店已打烊 | 返回门店但营业状态为关闭 | 从候选中剔除；若全部关闭，提示用户当前时段无可下单门店 |
| 目标门店不支持所选就餐方式 | 下单时返回错误 | 说明原因，改推支持该方式的门店，不要静默切换 |

## 2. 餐品类异常

| 情况 | 处理 |
|---|---|
| 到达时段无任何可售餐品 | 明确说明，并给出下一时段的可售预览；不要跨时段硬凑方案 |
| 偏好无匹配餐品 | 先如实说明「没有匹配 X 的餐品」，再询问是否放宽偏好；**不要**悄悄换成别的 |
| 餐品在购物车阶段售罄 | `calculate-price` 或 `create-order` 返回失败时，剔除该餐品后重算，并告知用户 |
| 套餐可替换项不满足偏好 | 调 `query-meal-detail` 取可替换项，列出替换后的新价格让用户确认 |

## 3. 优惠券类异常

| 情况 | 处理 |
|---|---|
| 券不满足门槛 | `effectiveDiscount` 返回 0，该券不参与该组合计价；**不要**为了用券而建议用户加购凑单 |
| 券不适用于当前门店 | 以 `query-store-coupons` 返回的门店可用券为准，我的券仅作补充判断 |
| 多张券可叠加 | 当前实现按「单券最优」处理（应付最低优先）。若 MCP 支持叠加，需在 `MCP_INTEGRATION.md` 中说明并扩展 `pickBestCoupon` |
| 券已过期 | 归入「已过期」档，仅提示不参与计价 |
| 自动领券失败 | 记录失败券，继续用已持有的券出方案，不阻断流程 |

## 4. 时间类异常

| 情况 | 处理 |
|---|---|
| 用户未提供出发时间 | 用 `now-time-info` 的当前时间，并**显式告知**用户"按当前时间计算" |
| 用户提供的通勤时长不合理（< 0 或 > 180 分钟） | 拒绝计算并请用户确认，不要静默截断 |
| 到达时间跨越凌晨 | 夜宵时段按跨零点逻辑计算剩余分钟 |
| 出发时间已过去 | 提示用户，并询问是改按当前时间还是改出发时间 |

## 5. 接口类异常

| 错误码 | 含义 | 处理 |
|---|---|---|
| 401 | Token 无效 / 过期 / 未提供 | 立即停止调用链，引导用户重新申请或检查配置；**不要**重试同一次调用 |
| 429 | 触发限流（> 600 次/分钟） | 指数退避重试：1s → 2s → 4s，最多 3 次；仍失败则如实告知 |
| 网络超时 | 无响应 | 最多重试 2 次，之后降级为「部分数据」方案并在结论中标注缺失项 |
| 返回结构变化 | 字段缺失 | 用可选链读字段，缺字段时跳过该条数据并计数，在结论中说明"已跳过 N 条异常数据" |

## 6. 资金安全类（最高优先级）

| 约束 | 说明 |
|---|---|
| 禁止自动下单 | 未获得用户显式确认前，不得调用 `create-order` / `party-order-create` / `mall-create-order` |
| 金额必须复核 | 下单前必须展示「原价 → 优惠 → 应付」，与实际调用 `calculate-price` 的结果核对一致 |
| 优惠券有副作用 | `auto-bind-coupons` 会写入账户，执行前必须告知并取得同意 |
| 积分兑换不可逆 | `mall-create-order` 会扣减积分，必须单独二次确认，不可与点单确认合并 |

## 7. 数据缺失时的输出规范

当关键数据拿不到时，输出应包含三要素：

1. **缺什么** —— 具体到工具名和字段
2. **为什么** —— 错误码或失败原因
3. **怎么办** —— 可行的替代路径

示例：

```
⚠ 未能获取门店菜单（query-meals 返回 401：Token 无效）。
   本次无法生成点单方案。
   请先检查 MCP Token 配置后重试。
```
