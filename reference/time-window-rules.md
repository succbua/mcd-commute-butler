# 供应时段规则

本文件定义「到达时还能买到什么」的判定依据，是通勤点单的核心前置逻辑。

## 1. 时段定义（北京时间）

| key | 名称 | 起 | 止 | 通勤场景备注 |
|---|---|---|---|---|
| `breakfast` | 早餐 | 05:00 | 10:30 | 竞争最激烈：早高峰 + 供应截止早，最容易「赶到店时已停售」 |
| `lunch` | 正餐 | 10:30 | 14:00 | 午休窗口，取餐排队最长 |
| `afternoon` | 下午茶 | 14:00 | 17:00 | 相对宽松 |
| `dinner` | 晚餐 | 17:00 | 22:00 | — |
| `late-night` | 夜宵 | 22:00 | 05:00 | 跨越零点，判定时按 `(end − now + 1440) % 1440` 计算剩余分钟 |

> ⚠ **各门店实际供应时间可能不同。** 上表仅用于「到达时是否赶得上」的**前置估算**。
> 真正的可售性必须以 `query-meals` 返回的门店实时菜单为准 —— 菜单里没有的餐品，
> 无论时段表怎么说，都不应出现在方案里。

## 2. 剩余分钟数的计算

```
剩余分钟 = (时段结束分钟 − 当前分钟 + 1440) % 1440
```

加 1440 再取模是为了正确处理跨零点的夜宵时段。

| 剩余分钟 | 判定 | 动作 |
|---|---|---|
| ≥ 60 | 充裕 | 正常出方案，无需特别提示 |
| 30 – 60 | 偏紧 | 在方案中提示「建议提前下单预约」 |
| 1 – 30 | **临界** | 必须在回复最前面给出显著告警，并优先给「出餐快」的方案 |
| ≤ 0（已过窗口） | 不可售 | 过滤掉该时段餐品，改按下一时段出方案 |

## 3. 临界状态的处理

当到达时窗口剩余不足 30 分钟，采取以下策略：

1. **告警前置**：第一句就说明还剩多少分钟，不要埋在方案后面。
2. **权重倾斜**：临时把「取餐耗时」权重从 0.30 提到 0.50，相应下调「价格」权重，优先推荐出餐快的组合。
3. **主动建议预约**：`create-order` 支持预约，应建议用户按到达时间预约，而不是到店再点。
4. **给出兜底**：明确告知「如果赶不上，到达时可选的将是 X 时段的餐品」，并列出该时段的前 3 个选项。

## 4. 跨时段切换

当到达时间落在时段边界附近（前一窗口剩余 < 15 分钟），同时给出两套方案：

- **A 套（赶末班车）**：当前时段仍可售、且出餐快的餐品
- **B 套（稳妥方案）**：下一时段已可售的餐品

让用户自己选，不要替他判断「值不值得赶」。

## 5. 与 MCP 的衔接

| 步骤 | 调用 | 用途 |
|---|---|---|
| 1 | `now-time-info` | 取当前时间（不要用模型自身的时间推断） |
| 2 | — | 本地计算到达时间与时段（`scripts/plan-commute-order.mjs`） |
| 3 | `query-meals` | 取门店**实时**可售菜单，覆盖本地时段表的估算 |
| 4 | `query-meal-detail` | 需要确认套餐内单品时逐个查询 |

时段表是「估算器」，门店菜单是「事实源」。两者冲突时，**以门店菜单为准**。
